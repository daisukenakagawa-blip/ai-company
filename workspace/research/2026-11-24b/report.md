## 3. 上位5案
### 第1位　KeyRelay：Lemon Squeezy と同じ形で使えるライセンスキー基盤（64点）
1. **事業名**：KeyRelay
2. **革新的な部分**：URL を1行変えるだけで、アプリのライセンス確認がそのまま動く。既存のキーと「有効化済みの端末」まで取り込むので、すでに売った客のアプリが止まらない。新しい販売は販売者自身の Stripe の Webhook でキーを自動発行し、当方はお金に触れない
3. **商品**：ライセンスキーの発行・有効化・確認・解除の API（ホスト型）、LS からの取り込み、Stripe 連携、購入直後のキー表示ページ
4. **購入者**：Lemon Squeezy でソフトウェア（デスクトップアプリ、プラグイン、CLI 等）を売り、License API を使っている世界中の個人開発者
5. **購入理由**：2027-03-31 に LS が止まり、License API の確認も止まると考えられる（LS は API 単体の終了日を明示していない）。移行先の Managed Payments・Paddle はキーを発行しない。自作すると、既存のキーの取り込みや端末数の管理を書き直す手間がかかる
6. **需要の証拠**：
   - LS の終了告知と比較表：[告知](https://www.lemonsqueezy.com/blog/saying-goodbye-to-lemon-squeezy)、[比較表](https://docs.lemonsqueezy.com/migration/comparison)（"Not included. Connect a fulfillment or licensing app"）
   - GitHub の公開コードで `api.lemonsqueezy.com/v1/licenses/validate` を呼ぶファイルが **525件**、`activate` が **268件**（2026-11-24 に GitHub のコード検索で計数。非公開のコードは数えられない）
   - 同じ分野の有料サービスが成り立っている：Keygen（無料は100ユーザーまで、上は有料：[料金](https://keygen.sh/pricing)）
   - 実際に何人が移行先を探しているか、何人が払うかは**未確認**
7. **自動集客**：
   - LS の移行チェックリストが販売者に「ライセンスキーをどう扱うか確認せよ」と求め、Managed Payments 側は「ライセンスアプリを接続せよ」と案内している。この行動の流れに置く
   - ① GitHub に OSS（MIT）として公開し、README を「lemonsqueezy license migration」で探す開発者に合わせる。GitHub 内の検索とコードの中のエラーで困った人が見つける
   - ② Stripe App Marketplace に「Managed Payments 用のライセンス発行アプリ」として出す（審査あり・要承認）。Managed Payments に移った販売者が、まさにここで探す
   - ③ npm に、LS の SDK と同じ関数名のクライアントを公開する
   - 次の客は、販売者のアプリの購入画面や「キー表示ページ」の小さな表示から来る（購入者の中にも開発者がいる）
8. **自動販売・決済・納品**：登録（API）→ 無料枠で取り込み・試用 → 上限を超えたら Stripe の Payment Link／サブスクで課金 → 機能はすぐ使える。客対応はドキュメントと API のエラー文で済ませる
9. **費用**：初期0円（Cloudflare Workers・D1 の無料枠：1日10万リクエスト、D1 書き込み1日10万行）。超えたら Workers 有料 $5/月（売上が出てから）
10. **収益構造**：月額の継続課金（例：無料＝キー100本まで、有料＝月 $9〜29）。キーの確認はアプリが動くかぎり毎日続くため、移行が終わった後も解約されにくい。**価格は仮で、売れる根拠は未確認**
11. **差別化**：Keygen・Polar はキーの仕組みが LS と違い、アプリ側の書き換えが必要。KeyRelay は LS と同じ入出力で、既存の端末 ID まで引き継ぐ
12. **模倣困難性**：低〜中。互換 API は誰でも作れる。強みは「移行の期限内に取り込んだキーと端末の記録」で、一度移ると別の場所へ移る理由がない（乗り換えの手間が堀になる）
13. **最大の失敗要因**：LS の販売者の多くが Polar（キー機能込み）など一式そろった別サービスに移り、ライセンス単体の需要が小さいこと。LS 自身が互換の移行先と提携すること。期限（2027-03-31）を過ぎると新規の流入が止まること
14. **0円での需要検証**：OSS を GitHub に公開し、ホスト版のベータ登録（無料）を開ける。2週間で「登録数・取り込まれたキーの数・確認 API の呼び出し数」を測る。これは実際に使われた数で、架空の数字は入らない
15. **総合評価**：64点

### 第2位　AI API・SaaS の料金／利用制限／提供終了の変更履歴 API（59点）
- **革新的な部分**：「いつ、何が変わったか」を日付つきで残す。上書きされる料金ページは後から埋められず、AI の学習データにもない
- **商品・購入者**：差分 API と通知。買うのは FinOps、購買、AI 開発者
- **需要の証拠**：競合調査ツール Klue の購入額は中央値 年3万ドル（[Vendr](https://www.vendr.com/buyer-guides/klue)）。安い層は PricingSaaS が月25ドル
- **自動集客**：公開の変更ログページと RSS、MCP サーバー（AI エージェントが「最新の料金」を調べるときに呼ぶ）
- **失敗要因**：無料の追跡がすでに多く、価格が崩れている。巡回には無料枠の上限がある
- **0円での検証**：対象を50ページに絞って1か月貯め、RSS の購読数と MCP の呼び出し数を測る

### 第3位　法人番号でつないだ日本の行政処分・許認可の変化通知（59点）
- **購入者・需要**：与信・取引先審査の担当。同種の Infopick は月5万〜20万円で掲載（売上は未確認）。日本の企業データにお金が払われていることは NJSS が示している
- **自動集客**：法人番号ごとの公開ページ（実データがある法人だけ）からの検索流入と、無料の通知登録
- **失敗要因**：公表期間・二次利用の条件が省庁ごとに違う（未確認）。個人事業主の処分は個人情報になる。検索に頼る比率が高い
- **0円での検証**：1つの省庁の処分情報だけで3か月の履歴を作り、検索流入と通知登録を測る

### 第4位　「Made with」表示つきの埋め込み部品（50点）
- 無料の埋め込み部品（例：お店のサイトの営業日カレンダー）に小さな表示を付け、見た人が自分のサイト用に作りにいく流れ。根拠は Tally・Carrd の自己申告
- 弱点：部品そのものの需要の根拠が弱い。模倣が簡単

### 第5位　x402 で課金する機械向けデータ API（49点）
- AI エージェントが自分で見つけて1回ごとに払う、唯一の「人が判断しない」売り方
- 弱点：実取引がごく小さく、上位の数社に集中。日本では USDC の受け取りと税務の手間がかかる。今は収益源ではなく、将来に向けた小さな実験として位置づける

## 4. 選定：第1位 KeyRelay
理由：「期限つきで、今まさに起きている強制移行」という、需要の発生がはっきり確認できる唯一の候補。お金に触れず（法的リスクが低い）、無料枠で動き、一度使われると毎日の確認で継続課金になる。

## 5. 試作（2026-11-24 完成・手元で確認済み）
`ventures/keyrelay/`
- LS と同じ形の activate／validate／deactivate（同じフォーム形式、同じ JSON の項目、端末数の上限、無効化、期限切れ）
- LS からの取り込み（キーと有効化済み端末の ID を引き継ぐ。2回目は重複を飛ばす）
- 販売者自身の Stripe の Webhook でキーを発行（署名を確認、二重発行なし）、購入直後のキー表示ページ
- 管理 API（キーの作成・無効化・利用統計）、1日ごとの呼び出し数の記録（課金の基礎）
- 確認：手元の Cloudflare 環境（wrangler と D1）で、有効化・上限・確認・解除・無効化・Webhook（正しい署名／不正な署名／再送）・キー表示を実行し、すべて期待どおり。取り込みは偽の LS API でテスト（PASS）
- LS 本体の API（`/v1/license-keys`・`/v1/license-key-instances`）の項目名とページ送り（`page[size]` 最大100、`links.next`）は、公式ドキュメントで照合済み。端末の `identifier` は有効化時の `instance_id` と同じ値と明記されている
