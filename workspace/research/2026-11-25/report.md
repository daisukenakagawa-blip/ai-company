# 新しい収益構造の検証（2026-11-25、Ver.2.1 第2・3・5・6・7条）

結論：**今回試した5つの構造は、すべて「開発前の合格条件」を満たさなかった（作らない）**。同時に、KeyRelay に直接の競合（Clavem）があることが分かった。最も有効だった発見は「公開されている利用数で、お金が流れている場所を先に探す」方法そのもの。

区別：【事実】一次資料・公開データで確認（URL付き）／【推測】AI の判断

## 2. 分かったこと（次に生かす）
- 【事実】Apify Store では、日本のマーケットプレイスのデータ取得（メルカリ等）の道具に累計150〜294人の利用者がいる。ただし他社サイトの取得は各社の規約に反する可能性が高く、**当社はやらない**
- 【事実】Apify・Shopify・Chrome Web Store・VS Code・npm などは、商品ごとの利用者数・レビュー数・ダウンロード数を公開している。GitHub の Issue 数よりも「お金・利用が実際に流れている場所」に近い
- 【推測】「既にお金が流れていて、供給が少なく、評価が低い（不満がある）」すき間を、この公開データからプログラムで探すのが、Ver.2.1 第4条（機械的な収集はプログラムで）と第6条（支払いの証拠を先に）に最も合う
- 【推測】KeyRelay は、Clavem に対して勝てる理由が弱い。無料ベータとして最小限で維持し、Stripe App 化はしない。12/2 の LS 公式案内で第三者の扱いが変わるかを見て再評価する

## 3. 次の方法：Demand Map（需要の地図）
- 入力：公開 API・公開ページの利用数（Apify Store API の totalUsers・30日利用者・価格、Shopify アプリのレビュー数と評価、Chrome Web Store・VS Code の利用者数、npm の週間ダウンロード）。すべて公開情報、規約で許された取得だけ
- 処理（プログラム）：カテゴリごとに「利用者の合計」「上位への集中」「平均評価」「新規参入の数」「価格帯」を集計し、需要が大きく・供給が少なく・不満が多い所を並べる
- 判断（Claude）：上位の候補を一次資料で確かめ、「AI で無料代替？」「規約」「到達経路」「合格条件7項目」で反証する
- 前提：`api.apify.com` が実行環境から取得できない（今回は WebFetch で取得）。オーナーが許可ウェブサイトに `api.apify.com` を足せば、毎朝自動で回せる
