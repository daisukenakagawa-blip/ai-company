# 新しい収益構造の発明と検証設計（Ver.2.2、2026-11-25）

分類：A＝需要と販売経路を確認／B＝需要は確認、経路・差別化は未検証／C＝需要そのものが未検証
「本格開発の条件」と「需要検証を始める条件」を分ける。区別：【事実】（出典あり）／【推測】

## 発明1：Continuity Relay（終わるサービスの「互換の受け皿」を連続で持つ）　分類 B
- 構造：サービスが終わっても、すでに配られたアプリ・プラグイン・端末は古い API を呼び続ける。その古い API と同じ形で答える「互換の受け皿」を、終了のたびに用意し、運用し続ける。KeyRelay はその1号
- 既存事業との違い：1つの商品ではなく「終了のたびに増える互換資産の束」を所有する。仕入れ（次の終了）は Market Gap Engine が自動で見つける
- 誰が何に払うか：古い API を呼ぶアプリを配っている開発者が、「アプリ側の大改修なしに、配布済みの利用者を動かし続ける」ことに払う（月額または確認 API の回数）
- 自動で収益が出る仕組み：配布済みアプリが毎日呼ぶ確認 API の回数が、そのまま課金の単位になる。開発者が作業しなくても利用が続く
- 自動集客の仕組み：期限（例 LS は2027-03-31）が近づくと、開発者は必ず「移行先」を探す。互換の受け皿は「URL を1か所変えるだけ」の最短経路として、移行の作業の途中で見つかる
- 需要の証拠：【事実】LS の直接互換を作った Clavem が年290〜1,990ドルで販売（https://clavem.io/）。競合の存在＝需要の証拠（Ver.2.2 第1条）。【推測・要確認】Parse（2017年終了）の後、互換の Parse Server をホストする事業（Back4App 等）が成立した前例
- 競合に勝てない部分を分解すると：大手（Clavem）は大きな終了だけを取る。**小さな終了（利用者が数百〜数千の API）は誰も互換を作らない**。そこを Gap Engine で拾い、OSS＋無料枠で最初に置く
- 0円の検証方法：①Gap Engine の過去の終了案件から「互換の受け皿がまだ無い小さな終了」を3件選ぶ（手元・無料）②各件で、古い API を呼ぶ公開コードの数・期限・代替の有無を一次資料で確かめる③1件だけ互換を試作（手元のテストまで）④公開は承認後
- 本格開発の条件：外部の開発者が1人以上、実際に URL を切り替えて使い続ける
- 不合格だった場合の改善案：受け皿の課金先を「開発者」から「その API を使う業務の利用者企業」に変える／互換をホスト型ではなく、自分で動かせる OSS ＋有料サポートにする

## 発明2：入札案件の「資格で絞った朝刊」＋判断の履歴（官公需）　分類 B
- 構造：公的な入札情報（官公需 API）を毎日集め、業種と入札参加資格で絞り、仕様書から締切・資格・場所を取り出して、毎朝 Slack かスプレッドシートに届ける。利用者の「検討・見送り」の記録が積み上がり、絞り込みが会社ごとに賢くなる（真似されにくい履歴資産）
- 誰が何に払うか：小規模な翻訳・イベント・IT 会社が、「月2万円の大手は高いが、無料ポータルを毎日見るのは手間」という問題に月980〜2,980円を払う
- 需要の証拠：【事実】NJSS 有料 7,295契約、四半期売上 9.75億円、解約率1.42%（https://www2.jpx.co.jp/disc/39790/140120260812518519.pdf）。【事実】NJSS のレビューに「値上がりで中小には負担」「Excel で一覧にしたい」（https://www.itreview.jp/products/njss/reviews）
- 反証：【事実】官公需 API を包んだ安い道具（月990円の MCP、Apify に6本以上）はほぼ使われていない。NJSS の契約数も頭打ち
- 無料の AI で代替できるか：単発の検索は代替される。毎日の監視・差分・資格の絞り込み・判断履歴の蓄積は代替されにくい（ただし差は小さい）
- 0円の検証方法：①オーナーが官公需ポータルの利用規約で商用利用・再配布の可否を確認 ②実行環境に www.kkj.go.jp を許可（いまは接続できない）③手元で1業種の朝刊を2週間作り、取りこぼしと件数を測る ④承認後、見本と順番待ちの受付を置く
- 成功条件：外部の登録10件、2週間使い続ける人3件、先払いか価格への同意1件
- 不合格だった場合の改善案：個人向けではなく、入札支援をしている行政書士・コンサル向けに「顧客ごとの朝刊」を卸す

## 追記：発明2 の最初の検証（2026-11-25 深夜、www.kkj.go.jp の許可後）
- 【事実】官公需 検索API に接続できた（例：「翻訳」で全期間 4,749件）。サイトの robots.txt は全体を拒否しているため、画面は取得せず公式 API だけを使う（API ガイド：https://www.kkj.go.jp/doc/ja/api_guide.pdf は「利用規約に従って」とだけ記載）
- 【事実】利用規約の本文は、夜間メンテナンス（午前2〜5時）で読めず未確認。確認できるまで外部には出さない
- 【事実】直近7日（11/18〜）の新着で、案件名に業種の語を含むもの：翻訳・通訳 0件／イベント・会議運営 6件／Web・システム 6件。**締切（TenderSubmissionDeadline）は全件空欄**で、締切は添付 PDF を読まないと分からない
- 【推測】①業種を絞ると1日1件以下で、「毎朝の朝刊」より「週1回のまとめ＋締切の抽出」の方が合う ②締切が API に無いことは、PDF から締切・資格を取り出す処理がそのまま付加価値になる根拠 ③翻訳は件数が少なすぎて単独では売れない。検索語の設計（案件名だけでなく本文）を変えて2週間測る
- 次：毎朝の定期タスクで `python3 ventures/_gap/kkj_digest.py 1` を2週間（〜12/9）回し、`workspace/kkj-digest/log.csv` に業種ごとの件数をためる。利用規約は日中に再確認

## 追記：官公需ポータルの利用規約（2026-11-25 朝に確認、https://www.kkj.go.jp/s/?tc=1）
- 【事実】第3条「APIの利用について」：①API を使うサイト・アプリに、官公需ポータルの API を使っている旨を明記し、ポータルへのリンクを設ける ②公序良俗・法令に反する利用は禁止 ③同時リクエスト数に制限があり、特定サーバーからの継続的な大量アクセスは禁止（具体的な制限は運営者へ問い合わせ）
- 【事実】商用利用・再配布を禁じる条文は無い。第5条：情報の収集と活用は利用者の責任
- 【推測】API の結果（案件名・機関・URL）を、出典明記とリンクつきで有料サービスに組み込むことは規約上は可能と読める。ただし ①添付 PDF（仕様書）は各発注機関のサイトにあり、それぞれの利用条件に従う ②「2. 入札情報は1日程度遅れて登録」「すべての提供を保証しない」ため、取りこぼしの説明が必要 ③法的な判断ではない（当社は弁護士ではない）。外部に出す前に、オーナーが同じ条文を読んで判断する
- 次：検証期間（〜12/9）は変えず、件数と抽出精度をためる
