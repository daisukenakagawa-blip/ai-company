# 収益原理の異なる20案（Ver.2.4、2026-11-25）
各案：①仕組み ②AIだから成立する理由 ③所有する資産 ④払う主体 ⑤支払いの瞬間 ⑥自動集客 ⑦自律成長 ⑧0円での実現 ⑨運用費 ⑩競合・模倣困難性 ⑪法律・規約 ⑫需要の検証方法
判定：A/B/C（需要と経路／需要のみ／需要未確認）。【事実】は出典あり、それ以外は推測

## 1. 拠出型 SaaS 価格ベンチマーク（日本）　B
①企業が自社の SaaS の契約単価（金額・席数のみ）を出すと、同じ SaaS の他社の価格帯が見られる。出さない企業は有料 ②形式がばらばらな請求書・見積から単価だけを抜き出し、匿名化・統計化を毎日自動で回す ③価格の分布と履歴 ④拠出しない企業、SaaS 管理ツール事業者（データ卸） ⑤ベンチマークを開いた瞬間（従量）か月額 ⑥更新の交渉前に「この価格は高いか」を調べる流れの中で見つかる。拠出者は自分の値を見るために他社にも勧める ⑦拠出が増える→分布が正確→見に来る人が増える→拠出が増える ⑧Cloudflare 無料枠＋Stripe ⑨ほぼ0 ⑩【事実】Vendr は購入者の提出が95%以上、国内 SaaS 管理ツールは他社比較を未提供（https://admina.moneyforward.com/jp/blog/saas-management-comparison ）。データを持つ Admina 等が機能追加すれば追い付かれる ⑪【事実】公取委：過去・匿名・統計処理・個社を特定できない形なら原則問題になりにくい。秘密保持条項で請求書そのものは出せない場合あり→金額と席数のみ ⑫拠出する意思と閲覧に払う意思を、見本の分布ページと予約で測る

## 2. AI が保守する LTS フォーク（見捨てられた OSS）　B〜C
①修正版のない脆弱性を抱えた人気パッケージを、互換を保ったまま修正・保守し続け、企業に保証・コンプライアンス証明を売る ②何百ものパッケージの修正・互換テストを人手なしで回し続ける ③修正済みフォーク群と互換テスト ④使い続けざるを得ない企業 ⑤年間の保証契約 ⑥脆弱性スキャナーが「修正版なし」を出した時点で企業は代わりを探す ⑦扱うパッケージが増えるほど、1社の依存を丸ごと任せられる ⑧npm・GitHub は無料 ⑨ほぼ0 ⑩【事実】HeroDevs 800社超・年3万ドル前後、Seal は AI でパッチを自動生成（$13M 調達）。素性の分からない個人の fork は信頼されない ⑪MIT・Apache は可、名前の紛らわしさに注意 ⑫空白（既存の fork も大手も扱っていない高ダウンロードの脆弱性）を機械的に数える→1件公開して依存数を測る

## 3. 入札公告の構造化レイヤーの貸出（士業・既存サービス向け）　B
①公告本文から締切・資格・地域を構造化し、原文の該当箇所つきで、入札支援の士業や既存の情報サービスに API・データで貸し出す ②全国数千機関の公告を毎日読み、抽出精度を記録で改善し続ける ③構造化データと抽出精度の履歴 ④士業・コンサル・既存サービス ⑤顧客ごとの月額（卸） ⑥士業1件が自分の顧客企業に配る ⑦顧客が増える→「見送り」等の記録が増える→絞り込みが良くなる ⑧官公需 API＋無料枠 ⑨ほぼ0 ⑩【事実】NJSS 7,295契約。データは公開なので模倣は容易、精度と履歴で差 ⑪官公需ポータルの規約が未確認 ⑫2週間の実測→規約確認→見本と予約

## 4. 終了サービスの「継続保証」サブスク　C
①開発者が月額で依存先を登録しておくと、依存先が終了したとき互換の受け皿を用意する（保険ではなく保守契約） ②終了の検知と互換の試作を常時自動で回す ③互換層の束 ④売上が依存先に左右される開発者 ⑤月額 ⑥依存先の終了の噂が出た時点で探される ⑦登録が多い依存先から互換を先に作る→受け皿が増える ⑧無料枠 ⑨ほぼ0（終了が起きると開発費） ⑩前例なし ⑪保険業法に当たらない形（保守契約）にする要確認 ⑫Continuity Relay の対象（売上が止まる API）で、事前登録が付くかを測る

## 5. 互換 API の束（Continuity Relay）　B
①終了した API と同じ形で答える受け皿を所有・運営 ②終了の自動検知と互換の自動試作 ③互換層 ④配布済みアプリの開発者 ⑤確認 API の利用量 ⑥移行作業の途中で「URL1か所」の受け皿が見つかる ⑦受け皿が増えるほど1社の移行を丸ごと受けられる ⑧無料枠 ⑨ほぼ0 ⑩【事実】LS では Clavem が先行 ⑪互換の実装は可、名前の使い方に注意 ⑫売上・業務・法令が止まる API の終了を Gap Engine から選ぶ

## 6. 移行コードの自動修正（期限つき API 変更）、マージされたら課金　C
①期限のある API 変更（モデル廃止、決済 API の版の変更など）に合わせて、リポジトリに修正 PR を自動で出し、マージされたら課金 ②数千のリポジトリの修正を同時に作れる ③変更ごとの変換規則 ④期限に追われる開発チーム ⑤PR がマージされた瞬間 ⑥PR 自体がリポジトリに残り、他の開発者の目に触れる ⑦変換規則が増えるほど対応範囲が広がる ⑧GitHub App は無料 ⑨AI 費（未確認） ⑩【事実】Codemod 系の資金調達あり（要確認）。受託に近い ⑪頼まれていない PR は迷惑行為、導入した利用者のリポジトリのみ ⑫GitHub Marketplace の導入数

## 7. SLA 証人（第三者の稼働記録＋返金申請の代行）　C（反証が強い）
【事実】AWS・Microsoft は顧客自身のログを要求し、第三者の記録は証拠にならない（https://aws.amazon.com/ec2-sla/ ）。返金は少額で現金でない。**不採用に近い**。改善案：顧客のログと連携して申請書を自動作成

## 8. 日本の行政手続きの「機械可読な要件」台帳　C
①補助金・許認可・届出の要件（締切・対象・必要書類）を構造化し、更新を追い、業務ソフトに組み込ませる ②数千の自治体ページの変化を毎日追う ③要件の時系列 ④会計・労務ソフト、士業 ⑤API 利用量 ⑥組み込んだソフトの利用者に自動で届く ⑦組み込み先が増える→誤り報告が増える→精度が上がる ⑧無料枠 ⑨0 ⑩補助金ポータル（jGrants）は公式 API あり ⑪自治体サイトの取得条件、法律助言に当たらない形 ⑫組み込み先の候補に見本を見せて意向を測る

## 9. オープンデータの「品質保証つき」再配布　C
①政府・自治体のオープンデータ（CC BY 等）の誤り・形式ゆれを毎日検査・修正し、差分つきで配る ②全データの検査を常時回す ③修正履歴 ④データを使う開発者・研究者 ⑤月額 ⑥元データの不具合を検索した人が見つける ⑦利用者の誤り報告が溜まる ⑧無料 ⑨0 ⑩無料の元データで足りる人が多い ⑪ライセンス表示 ⑫元データの不具合の問い合わせ件数

## 10. AI エージェント向けの「日本の公的情報」ツール（法人契約・月額）　C
